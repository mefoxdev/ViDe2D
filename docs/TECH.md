# Vide-studio — выбор технологий (черновик, Go)

Vide-studio — единая оболочка для Vimg (пиксельарт), Vtune (чиптюн), VCode (TrueDSL), а также запуска игры и публикации в ViDe-store. В README такого компонента пока нет — состав уточнить.

## Критерии
1. Pure Go, без cgo (простая кросс-сборка, один бинарник).
2. Пиксельарт: целочисленный масштаб, без сглаживания.
3. Общий стек с рантаймом: превью игры внутри студии = тот же код, что в рантайме.
4. Низкая задержка аудио (Vtune).
5. Один процесс, единый набор виджетов для всех редакторов.

## Кандидаты
| Вариант | Плюсы | Минусы |
|---|---|---|
| **Ebitengine v2.10** | Pure Go на Windows/macOS/Linux (с 2.10), 2D, пиксельарт «из коробки», аудио (oto), совпадает с рантаймом | Не GUI-тулкит: нет виджетов; нужен Go 1.25+ |
| Gio | Pure Go, immediate mode | Мало виджетов, API до 1.0, свой цикл — не делится с рантаймом |
| Fyne | Много виджетов, большое сообщество | Нужен cgo, «нативные» виджеты, плохо подходит для пиксельного холста |
| Cogent Core | Retained-mode, богатый | Нужен cgo (Vulkan/glfw), большое дерево зависимостей |
| cimgui-go (Dear ImGui) + backend Ebitengine | Готовые виджеты для инструментов, докинг | Обёртка над C++ → cgo |

(Оценки cgo/виджетов Gio, Fyne, Cogent Core — из одной сравнительной статьи, написанной автором конкурирующего тулкита; перепроверить перед финальным решением.)

## Решение
- **Окно, рендер, ввод, аудио: Ebitengine v2.10+** (`ebiten/v2`, `ebiten/v2/audio` поверх oto, purego под капотом).
- **UI: свой небольшой immediate-mode слой поверх Ebitengine** (кнопка, панель, список, слайдер, поле ввода, вкладки, докинг), чтобы не тянуть cgo. Резерв — `ebitenui` (retained-виджеты; зрелость не проверена).
- **Холст Vimg**: `ebiten.Image` + `FilterNearest`, данные слоёв — `image.RGBA`/индексированные палитры в памяти.
- **Vtune**: собственный синтез (square/pulse, triangle, noise) в `io.Reader` для `audio.Player`; детерминированный секвенсор.
- **VCode**: собственный текстовый буфер + рендер шрифта (`text/v2`), лексер/парсер TrueDSL из пакета языка.
- **Форматы/проекты**: общие пакеты `formats/` (Vimg, Vtune, TrueDSL), общие с рантаймом; версионирование и тесты на повреждённые файлы.
- **Тесты**: логика отдельно от UI (чистые Go-пакеты), `go test`.

## Риски
- Самый тяжёлый узел — многострочный текстовый редактор (IME, выделение, прокрутка) в самописном UI. Если затянется — рассмотреть ebitenui или вынести редактор кода.
- Linux всё равно требует системные библиотеки окна/графики/аудио в рантайме (без заголовков для сборки).
- Go на машине сейчас не установлен.

## Рантайм (vide-run)
- **Процессы**: игра запускается отдельным процессом `vide-run [-root dir] <project.vide.json | сцена>` (`cmd/vide-run`, ядро — `internal/runtime`). Кнопка Play в студии сохраняет текущую сцену и стартует `vide-run` (рядом с исполняемым файлом студии, затем в PATH); падение игры студию не затрагивает. Запускаются только сцены; один запущенный экземпляр за раз.
- **Загрузка**: формат v4 через `internal/project`; `ref`-экземпляры раскрываются рекурсивно из папки проекта (защита от циклов, глубина ≤ 8, ≤ 200 000 сущностей), шаблоны (`template`) в мир не попадают. Пути проверяются валидаторами (`projfs`, `assets`), символические ссылки и файлы > лимита отвергаются. Скрипты TDSL выполняет VM (`internal/tdsl/vm`, этап 1 — см. ниже); включаются опцией `Options.Scripts`.
- **TrueDSL, этап 1 (ядро)**: компилятор AST → байткод + стековая VM (`internal/tdsl/vm`, без зависимостей от рантайма и Ebitengine, связь с миром — интерфейс `vm.Host`). Скрипт компилируется при первом шаге объекта (после проверки `tdsl.Check` с именами объектов сцены); при ошибках скрипт не запускается, ошибки пишутся в `Log`, игра идёт дальше. Порядок кадра: `Behavior.Step`, затем фазы start → ввод → update → таймеры `every`, каждая — по всем объектам в порядке дерева сцены (`Phased`); затем уничтожение объектов (`destroy`) и `Input.Advance`. Числа — float64, каждый результат обёрнут в `float64()` (запрет FMA), `random` — PCG32 с зерном `Options.Seed`; `per second` = значение / `tick_rate`, `every N seconds` считается шагами. Лимиты из safety.md (200 000 шагов/кадр, 50 000/обработчик, глубина 64, 100 000 элементов, 10 000 символов); превышение останавливает только обработчик (TD401/TD402/TD404). Позиции `Entity` — float64.
  - Поддерживается: `var`, присваивания, выражения, текст со вставками, списки, `if/while/repeat/for each`, свои команды `to` с `return`, события `start`/`update`/`every`/`key … pressed|held|released`, `move`, `move to`, `turn`, `show`/`hide`, свойства `x y width height angle visible image tint flip layer tag name text font_size` у `self`, `print`, `destroy` (себя), списковые команды, функции `min max abs round floor ceil sqrt random pick upper lower number opposite`.
  - **Этап A1 (касания, создание, сообщения, мышь, shared/use)** реализован: события `touch`/`stop touching`/`click`/`message`, `other`/`value`, `touching`/`avoiding`, `find`/`all`/`count`/`exists`/`distance`, чужие объекты и их переменные (`Hero.x`, `Hero.hp`), `spawn` (шаблоны `Template`, ≤ 5 000 живых копий, TD403) и `destroy` чужих объектов, `send`/`when message` (порядок отправки, ≤ 1 000 за кадр, TD402), `mouse.x/y/held`, `shared` (все скрипты проекта компилируются до первого кадра), `use` (только `to`, путь внутри проекта через `Source.SafeFile`). Точные правила — в `docs/truedsl/reference.md` («Точные правила касаний…»). Порядок кадра: init → start → ввод (клавиши, `click`) → update → `every` → касания → доставка сообщений → добавление созданных → удаление. Столкновения (`internal/runtime/collide.go`): коробки AABB в мировых координатах (без размера — объединение коробок потомков, иначе точка), равномерная сетка 64 px на каждую метку, перестраивается лениво при изменении состава мира (перестройка списывается из шагов кадра, n/16), смена метки скриптом правит индекс на месте, обновляется по `World.Place`; кэш коробки группы сбрасывается по объекту (сам объект и все его предки) и живёт один шаг, пересчёт тоже списывается; объекты, созданные `spawn` в этом кадре (`Entity.pending`), в запросах не участвуют; результаты — всегда в порядке сцены; работа каждого запроса списывается из шагов кадра (1 шаг за 4 коробки). Мышь: `InputState.SetMouse` получает координаты вида (через `Placement.ToView`), миру добавляется камера.
  - Пока не поддерживается (ошибка выполнения TD499 «пока не поддерживается в этой версии», при загрузке — предупреждение): `wait`/`slide`, звуки (`play`, `stop music`), `go to scene`/`restart scene`, `remember`/`recall`, `sin`/`cos`. Escape — обычная клавиша для скриптов; игру закрывают Ctrl+Q или окном. Координаты `x`/`y` скрипта — относительно родительской группы (дети двигаются вместе с родителем, `destroy` группы удаляет и её содержимое). При выгрузке чанка состояние его объектов (положение, переменные скриптов, список уничтоженных) сохраняется в `ChunkState` и возвращается при загрузке; точка расширения для будущей офлайн-симуляции выгруженных чанков — тот же `ChunkState`, она не реализована. Угол `angle` и `layer` хранятся, но пока не влияют на рисование.
- **Карта**: оптимизированная карта состоит из чанков 64×64 тайла, которые грузятся и выгружаются независимо (`World.LoadChunk/UnloadChunk`; политика радиуса вокруг вида — `UpdateChunks`). Неоптимизированная карта загружается целиком.
- **Фиксированный тик**: симуляция идёт шагами с частотой `tick_rate` сцены (60/90/120 Гц) и отделена от рендера. `Clock` — аккумулятор без обращения к системным часам (время в нс×частота, поэтому ровно N·rate шагов за N секунд; при долгой паузе шаги отбрасываются свыше rate/4). Системное время читается только на границе, в `Game.Update`. Рендер интерполирует между `PrevX/PrevY` и `X/Y`.
- **Вид и масштаб**: мир рисуется в буфер `view.w × view.h`, затем масштабируется в окно (`Fit`). Режим `pixel`: только целый масштаб (≥ 1), nearest, целочисленный сдвиг, чёрные поля (letterbox), позиции округляются до пикселя. Режим `normal`: плавное масштабирование с сохранением пропорций. Камера пока статична в (0,0).

### Корень проекта и изоляция
Намеренная изоляция (для работы ИИ-агентов над проектом): ничто не может выйти за корень проекта. Угадывания по `game/scenes/` нет.
- **Корень** = папка, где лежит открытый/переданный файл (`projfs.FileRoot`), ничего выше не ищется и не читается: игра не должна выходить за папку, которую выбрал пользователь. Сцена из `game/scenes/` без `-root` получает корнем `game/scenes/`, и её ссылки `game/objects/...` не найдутся. Поэтому это явная ошибка, а не тихий пустой проект: `vide-run` (без `-root`) отказывается стартовать (код 2), студия пишет предупреждение при открытии, панель проекта подсказывает, а Play отказывается запускать; сообщение (`projfs.NestedHint`) называет папку проекта: откройте её `project.vide.json` или передайте `-root <папка проекта>`. Студия при Play всегда передаёт свой корень явно.
- **Доступ к файлам**: все чтения и записи проекта идут через `projfs.Root` (поверх `os.Root`): проверка «нет ссылок/junction/irregular, нет `..`» и открытие — одна операция (нет TOCTOU), выйти из папки нельзя даже при ошибке проверки. `SafeFile`/`NoLinks` остались для совместимости; для чтения используйте `projfs.OpenFile/ReadFile`, для записи `WriteFile` (атомарно) и `CreateNew`. Документы читаются с лимитом `projfs.MaxDocBytes` (16 МБ) везде: рантайм, студия, клиент.
- **`-root dir`** — явное переопределение: корень ровно `dir` (должна быть папкой), файл сцены обязан лежать внутри, иначе ошибка «the scene … is outside the project root». Сам `dir` может быть ссылкой (его выбрал пользователь).
- **Пути** в документах (`ref`, `texture`, `script`, `use`, звуки) — относительные, со `/`, без `..`, абсолютных путей, `\`, NUL, `./`. Ни один компонент пути ниже корня (и сам файл сцены) не может быть символической ссылкой; проверка — `projfs.SafeFile` (чтение) и `projfs.NoLinks` (создание/запись в студии), используют их `runtime.Source`, `assets.Decode`, студия (`openDoc`, ссылки, скрипты, сохранение, «New»). Звуки: загрузчика пока нет; когда появится, обязан ходить через `projfs.OpenFile`.
- Проверка лексическая плюс `Lstat` по компонентам; гонка «проверка — открытие» (подмена файла ссылкой между ними) не закрыта: защита рассчитана на статичный проект, не на злонамеренный параллельный процесс. Без `openat`/`O_NOFOLLOW`.
- Тесты: `internal/projfs/root_test.go`, `internal/runtime/root_test.go`, `TestStudioRefusesLinkedDocs`, `TestStudioDocSizeLimitAndLinkedWrites`, `TestNestedSceneRefusesPlay`.

### Вывод игры в консоль студии
Play читает stdout и stderr дочернего процесса построчно (горутины-читатели только кладут строки в канал на 1024 строки и считают потерянные; в консоль пишет только `Update` через `pollPlay`). Строка режется до 300 рун, управляющие символы (в т.ч. ESC) и неверный UTF-8 заменяются; показывается не больше 200 строк в секунду, остальное — одно сообщение «N lines not shown». Строки идут с префиксом `[game]`; отчёт о завершении (с хвостом stderr) остаётся и приходит после всего вывода. Тесты — `internal/studio/play_test.go` (фейковый ребёнок через `os.Args[0]`).
