# Building ViDe2D

Programs: `vide-run` (runtime), `vide-client` (library of games + launcher),
`vide-studio` (editor; desktop only). All scripts are in `build/`, output goes
to `dist/` (git-ignored). Flags: `-trimpath`, `-buildvcs=false`, `-s -w`, and
`-X main.version=$(git describe --tags --always --dirty)` (override with
`VERSION=1.2.3`). `vide-client -version` prints it.

## Everything

    build/all.sh [-desktop] [-android]     # no flags = both

Desktop targets are built; Android is built only if its prerequisites exist,
otherwise a list of what is missing is printed and the rest still succeeds.

## Linux and Windows desktop (pure Go, CGO_ENABLED=0)

Prerequisites: Go (see go.mod), GNU `tar` (`gtar` on macOS: `brew install gnu-tar`) and `gzip`; `zip` for Windows archives. The scripts stop with a clear message if one is missing or a step fails. No C
compiler, no system libraries at build time (Ebitengine uses purego).

    build/linux.sh [amd64] [arm64]     -> dist/linux-<arch>/ and dist/vide2d-<version>-linux-<arch>.tar.gz
    build/windows.sh [amd64] [arm64]   -> dist/windows-<arch>/*.exe and ...-windows-<arch>.zip

Windows client and studio use `-H=windowsgui` (no console window); `vide-run`
keeps the console for script `print` output. On Windows itself:
`.\build\windows.ps1 -Arch amd64`. Linux runtime needs the usual X11/Wayland
and OpenGL libraries at run time. The tar.gz and the zip made by `windows.sh` are reproducible (sorted,
fixed owner and mtime; `zip -X`). `windows.ps1` uses Compress-Archive, which is not.

## Client

`vide-client [-games dir]` lists games from `~/ViDe2D/games` (default). A game
is a subfolder with `project.vide.json` (or a scene in `game/scenes/`), or a
loose `*.vide.json`. Up/Down + Enter, click or tap starts a game; F5 rescans.
On desktop it starts `vide-run` as a child process, looked up next to the client
executable, then in PATH (so keep the files of one `dist/<os>-<arch>/` together).
Symbolic links in the games folder are not followed. Logic lives in
`internal/client` (`Launcher`: `ProcessLauncher` on desktop, `InProcessLauncher`
on Android/iOS, chosen by `ForPlatform`).

## Android (client + runtime, no studio)

`internal/mobile` is the ebitenmobile entry (`SetGamesDir`, `Dummy`, game set
in `init`); it runs the client in-process. `build/android/` is a Gradle wrapper
app (`MainActivity` hosts `EbitenView`); see `build/android/README.md`.

Prerequisites:
- Go and a JDK 17+ (`java` in PATH).
- Android SDK (`ANDROID_HOME`) with `platforms;android-34`, `build-tools;34.0.0`.
- Android NDK (`ANDROID_NDK_HOME`, or `$ANDROID_HOME/ndk/<version>`: the newest installed one by version order, or the one named in `NDK_VERSION`).
- `go install github.com/hajimehoshi/ebiten/v2/cmd/ebitenmobile@v2.10.0` with
  `$(go env GOPATH)/bin` in PATH.
- Gradle 8.x (or Android Studio) to produce the APK; run `gradle wrapper` once
  in `build/android`.

Commands:

    build/android.sh            # AAR, then APK
    build/android.sh -aar-only  # build/android/app/libs/videlib.aar only

Outputs: `build/android/app/libs/videlib.aar`,
`build/android/app/build/outputs/apk/debug/app-debug.apk` (debug-signed; release
signing is not configured). The script exits with code 2 and instructions if
any prerequisite is missing.

## Verification status

Verified on Linux amd64: Linux amd64/arm64 and Windows amd64/arm64 builds all
succeed (`build/all.sh -desktop`), outputs have the right formats (ELF, PE32+
GUI), `go vet ./...`, `gofmt`, `go test ./...` pass, including headless tests
for scanning and launcher selection (`internal/client`). The client UI was
not opened in a window and no Windows binary was run.

NOT verified: the whole Android path. This machine has no JDK, Android SDK,
NDK or ebitenmobile, so `internal/mobile` was only compiled for the host, the
Gradle project and `MainActivity` were never built, and the Java class names
generated by ebitenmobile (`com.vide2d.client.mobile.EbitenView`, `Mobile`) are
assumed from its naming rules. Expect to fix small things on the first run.
